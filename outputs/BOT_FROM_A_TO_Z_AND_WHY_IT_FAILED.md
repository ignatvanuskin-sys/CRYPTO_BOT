# CryptoBot: что это за бот от А до Я и почему получилась нерабочая версия

Дата: 28.08.2026

## Короткий честный вывод

Это не один законченный бот, а попытка одновременно собрать три продукта:

1. Telegram-бот для соревнования по виртуальной торговле.
2. FastAPI-бэкенд для Telegram Mini App.
3. Фоновую систему рынка: цены BingX, TP/SL, расчёт PnL и завершение турниров.

Код для всех трёх частей частично написан, но в Railway реально запущены только:

- `CRYPTO_BOT` — Telegram polling;
- `Postgres` — база данных.

FastAPI API и worker не запущены. Поэтому внешне это выглядит как бот, который обещает полноценную торговую арену, но фактически не имеет полностью работающего рынка, Mini App и фоновой обработки. Это главная причина провала.

Предыдущая формулировка «production-ready» была слишком оптимистичной. Точнее было сказать: «часть backend-логики покрыта тестами, но продукт не прошёл сквозной приёмочный тест в реально развернутой конфигурации».

---

## 1. Что бот должен делать

Идея продукта — виртуальная крипто-биржа в Telegram:

- пользователь открывает бота;
- получает демо-баланс, обычно $10 000;
- входит в текущий турнир;
- выбирает BTC, ETH или SOL;
- открывает LONG или SHORT;
- получает цену от BingX perpetual market;
- видит виртуальный PnL;
- может поставить Take Profit / Stop Loss;
- соревнуется по ROI;
- после завершения турнира получает место в рейтинге и потенциальный приз.

Это не реальная торговля и не подключение пользовательских средств. `paper_adapter.py` создаёт виртуальные ордера, позиции и проводки в базе.

---

## 2. Как должна выглядеть полная система

### Telegram-бот

Файл запуска: `bot/main.py`.

Он должен:

- запустить aiogram polling;
- подключить Telegram command menu;
- открыть DB session для каждого update;
- зарегистрировать paper-роутеры профиля, торговли и рейтинга;
- держать PostgreSQL advisory lock, чтобы не работали два polling-процесса одновременно.

Основной пользовательский путь:

```text
/start
  -> User
  -> TradingAccount
  -> активный Competition
  -> CompetitionParticipant
  -> главное меню

/trade
  -> актив
  -> LONG / SHORT
  -> размер позиции
  -> TP / SL
  -> подтверждение
  -> open_position()
  -> PaperOrder + PaperPosition + AccountLedger
```

### FastAPI

Файл: `apps/api/main.py`.

API должен обслуживать Mini App:

- `/api/auth/telegram` — проверка Telegram `initData` через HMAC;
- `/api/me` — текущий пользователь;
- `/api/account` — баланс и equity;
- `/api/account/stats` — статистика сделок;
- `/api/markets` — инструменты;
- `/api/positions` — позиции;
- `/api/positions/{id}/close` — закрытие позиции;
- `/health`, `/ready`, `/metrics` — технические endpoints.

### Worker

Файл: `workers/main.py`.

Он должен одновременно запускать:

1. `price_poller` — получать тикеры BingX и записывать bid/ask в `market_snapshots`.
2. `tp_sl_engine` — обновлять текущие цены и закрывать позиции по TP/SL.
3. `competition_lifecycle` — завершать турниры, фиксировать leaderboard и призы.

Worker также имеет PostgreSQL advisory lock.

### PostgreSQL

База должна быть общей для Telegram-бота, API и worker.

Критичные таблицы нового режима:

- `trading_accounts`;
- `account_ledger`;
- `paper_orders`;
- `paper_positions`;
- `instruments`;
- `market_snapshots`;
- `competitions`;
- `competition_participants`;
- `leaderboard_snapshots`;
- `competition_prizes`.

В проекте также остаётся старый TradeWeek-контур с таблицами и сервисами legacy-режима. Это сделано для сохранения старых данных, но усложняет систему.

## 3. Как считается цена

Правила в backend заложены правильные:

- LONG открыть по ASK;
- LONG закрыть по BID;
- SHORT открыть по BID;
- SHORT закрыть по ASK.

Деньги и PnL считаются через `Decimal`, а не через float. Есть idempotency keys, блокировка аккаунта и проверки маржи.

Но эти правила работают только если worker реально записывает свежие snapshots в PostgreSQL. Без worker backend видит старые или отсутствующие данные и должен отклонять торговлю как `Market data stale` / `Market data unavailable`.

## 4. Что реально задеплоено

В Railway сейчас только два сервиса:

```text
CRYPTO_BOT  -> PYTHONPATH=/app alembic upgrade head && python -m bot.main
Postgres    -> база
```

Команда из `nixpacks.toml` и `Procfile` запускает только Telegram-бота. В них нет:

```text
uvicorn apps.api.main:app --host 0.0.0.0 --port $PORT
python -m workers.main
```

То есть фактическая архитектура сейчас такая:

```text
Telegram -> CRYPTO_BOT -> Postgres
                         ^
                         |
                    нет worker

Mini App -> нет запущенного API
```

Это не трёхсервисная production-система из документа. Это один polling-процесс и база.

В логах Railway действительно виден только запуск Telegram polling. Логов `workers.main`, price poller, TP/SL engine или FastAPI нет.

## 5. Почему Mini App выглядит как заглушка

`apps/miniapp/src/App.tsx` — это минимальный scaffold, а не готовое приложение.

Фактические проблемы:

- график отображается буквально как `[ CHART BTCUSDT ]`;
- вкладка Positions содержит текст `Transactions list — fetch /api/positions`;
- вкладка Profile содержит текст `Profile stats — fetch /api/profile`;
- реального запроса позиций нет;
- реального запроса профиля нет;
- endpoint `/api/profile` в backend не реализован;
- баланс загружается только один раз при открытии;
- после открытия сделки баланс не обновляется;
- ошибки показываются через обычный browser `alert()`;
- нет loading-состояний и нормальных error states;
- `parseFloat()` используется на финансовом frontend-пути;
- поле `qty` не объясняет, это количество монет или размер позиции в USD;
- в UI написано `Balance $10,000`, даже если реальный баланс пользователя уже другой;
- Mini App не собран и не опубликован отдельным статическим сервисом.

Поэтому называть это готовым Mini App нельзя. Это экран-заготовка для дальнейшей разработки.

## 6. Почему Telegram-бот тоже ощущается сырым

### Смешаны разные версии интерфейса

В репозитории одновременно есть:

- старый TradeWeek UI;
- новый paper-trading UI;
- русские тексты;
- английские названия в Mini App;
- обычные Unicode emoji;
- custom Telegram premium emoji;
- старые callback names и новые `nav:*` callback names.

Это результат не единого дизайна, а слияния нескольких веток и подходов.

### Бизнес-правила зависят от состояния базы

Торговля возможна только при наличии активного и неистёкшего турнира. Если турнир не создан, закончился или данные рынка устарели, пользователь получает отказ. Само по себе это правильно, но продукт не даёт хорошего пути восстановления:

- нет нормального экрана «рынок запускается»;
- нет понятного статуса worker;
- нет кнопки повторить загрузку;
- нет админского сценария запуска турнира для обычного оператора.

### Реальные уведомления не доведены до продукта

Есть `services/notifications.py`, но это best-effort код. Он не заменяет полноценную систему уведомлений, очередей и повторных попыток. Ошибка Telegram не должна ломать финансовое состояние — это правильно, но пользователь при этом может не получить сообщение о закрытии позиции.

## 7. Технические причины, почему получилось плохо

### Причина №1: собрали backend, но не собрали runtime

Самая серьёзная ошибка — считать написанные файлы развернутой системой.

Наличие `workers/main.py` не означает, что worker работает. Наличие `apps/api/main.py` не означает, что API доступен. Для продукта важны живые процессы, маршруты, DNS, env и сквозной сценарий.

В Railway был оставлен legacy `Procfile`, который запускает только bot. Это сохранило polling, но убило основную runtime-часть paper trading.

### Причина №2: тестировали отдельные функции, а не продукт

Результат `33 passed` выглядит хорошо, но он не отвечает на вопросы:

- доступен ли Mini App из Telegram;
- работает ли API в Railway;
- запускается ли worker;
- появляются ли реальные snapshots в PostgreSQL;
- открывается ли позиция в Telegram после реального tick;
- закрывается ли она worker-ом по TP/SL;
- видит ли пользователь обновившийся баланс;
- работает ли полный путь `/start -> trade -> position -> close -> leaderboard`.

8 PostgreSQL race-тестов были пропущены, потому что Docker daemon не работал. SQLite-тесты не являются заменой проверке реальной PostgreSQL-конкурентности.

### Причина №3: не был проведён настоящий acceptance test после deploy

Проверка в репозитории была в основном backend/unit/integration-level. После деплоя не был пройден сценарий настоящего пользователя в Telegram и Mini App.

Именно такой тест сразу показал бы:

- API не запущен;
- worker не запущен;
- график — placeholder;
- Positions/Profile — placeholder;
- рынок не обновляется.

### Причина №4: слишком много legacy-кода оставили рядом с новым кодом

Старый и новый контуры не были полностью разделены физически. В проекте сосуществуют:

- старый weekly trading;
- новый competition paper trading;
- старый `price_cache`;
- новый `market_snapshots`;
- старые позиции и новые paper positions;
- старые handlers и новые handlers.

Флаг `TRADING_MODE` уменьшает риск, но не заменяет архитектурное разделение. Такая система легко запускается «не тем» процессом или показывает несовместимый UI.

### Причина №5: merge веток был сделан на уровне файлов, а не продукта

Ветки содержали одновременно:

- UI custom emoji/Russian interface;
- новые paper trading handlers;
- новые API/worker файлы;
- изменения миграций;
- legacy compatibility.

Конфликты были разрешены так, чтобы код компилировался и тесты проходили, но это не гарантирует целостность пользовательского опыта. В результате часть UI-идеи сохранилась, а часть новой функциональности осталась scaffold-уровня.

## 8. Дополнительные реальные проблемы

1. `apps/api/main.py` в `_market_data_state()` напрямую вычитает timezone-aware `now` из DB timestamp. На PostgreSQL с naive `TIMESTAMP` это может дать тот же конфликт aware/naive, который ранее уже был найден в другом сервисе.
2. CORS разрешает `*`, если `WEBAPP_URL` не задан.
3. У API нет rate limiter.
4. `/api/markets/{symbol}/candles` честно возвращает пустой массив, то есть графика нет.
5. Метрики хранятся в памяти процесса и теряются после рестарта.
6. Worker не был развернут, поэтому TP/SL и lifecycle фактически не выполняются.
7. Один сервис совмещает миграции и Telegram polling; это неудобно для безопасного rollout.
8. Нет отдельного release/migration процесса.
9. Нет полноценной production-мониторинговой схемы: алертов, внешнего uptime check, ошибок API, состояния market feed.
10. Реальные выплаты призов не реализованы — призы только назначаются в базе.

## 9. Что нужно сделать, чтобы это стал нормальный бот

### P0 — сначала сделать реально работающий runtime

Создать в Railway минимум три сервиса из одного репозитория:

```text
crypto-bot:
  alembic upgrade head && python -m bot.main

crypto-api:
  uvicorn apps.api.main:app --host 0.0.0.0 --port $PORT

crypto-worker:
  python -m workers.main
```

Во все три передать одинаковые:

- `DATABASE_URL`;
- `TRADING_MODE=paper`;
- `REQUIRE_POSTGRES=true`;
- `BOT_TOKEN`;
- `WEBAPP_URL`;
- `ADMIN_TELEGRAM_IDS`;
- настройки BingX.

После этого проверить не по статусу Railway, а по фактам:

- API отвечает `/health` и `/ready`;
- в `market_snapshots` каждую пару секунд меняется timestamp;
- worker пишет price poll logs;
- TP/SL worker закрывает тестовую позицию;
- Telegram открывает и закрывает позицию;
- leaderboard обновляется.

### P1 — закончить Mini App

Нужно убрать заглушки и реализовать:

- настоящий candlestick chart;
- `/api/positions` загрузку и обновление;
- `/api/account/stats` загрузку;
- закрытие позиции с подтверждением;
- loading/error states;
- refresh после сделки;
- server-side Decimal-compatible ввод;
- понятный выбор notional или quantity;
- адаптацию под Telegram theme;
- отдельный build и hosting.

### P2 — упростить продукт

На время убрать из production:

- legacy weekly UI;
- старые команды, не относящиеся к paper trading;
- вторую модель рынка;
- все неиспользуемые callback paths;
- неиспользуемые старые таблицы из пользовательского пути.

Сначала нужен один чистый сценарий:

```text
/start -> активный турнир -> выбрать BTC -> LONG -> $500
-> получить цену -> открыть -> увидеть позицию
-> worker обновляет PnL -> закрыть -> увидеть результат в рейтинге
```

### P3 — заново провести приемку

Обязательный сценарий после исправлений:

1. Новый Telegram-пользователь.
2. `/start`.
3. Создание аккаунта.
4. Присоединение к активному турниру.
5. Открытие LONG по ASK.
6. Открытие SHORT по BID.
7. Проверка DB snapshot.
8. Обновление PnL worker-ом.
9. TP/SL закрытие.
10. Ручное закрытие.
11. Повторный клик и idempotency.
12. Завершение турнира.
13. Leaderboard и призы.
14. Повторное завершение без дублей.
15. Тот же тест через Mini App.

## Итог

Получилась «хуйня» не из-за одной ошибки в PnL или одной кривой кнопки. Получился разрыв между тремя уровнями:

```text
что задумали  !=  что написали  !=  что запустили
```

Задумали Telegram + Mini App + API + worker + BingX + competitions.

Написали большую часть backend-каркаса и набор тестов.

Запустили в Railway только Telegram polling и PostgreSQL.

Пока не запущены API и worker, а Mini App остаётся scaffold-заготовкой, это нельзя считать готовым торговым ботом. Самая правильная стратегия — не добавлять ещё новые фичи, а сначала довести один сквозной пользовательский сценарий до рабочего состояния в реальном Railway runtime.
