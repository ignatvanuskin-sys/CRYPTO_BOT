# AGENTS.md — TradeWeek: Telegram-бот виртуальной торговой биржи

> Рабочее название проекта — `TradeWeek` (замени на своё). Документ адресован AI-агенту-разработчику и содержит полную спецификацию MVP без Mini App. Ожидаемый результат — единый архив с кодом, миграциями и тестами, код не выводится в чат, перед сдачей — подтверждённый зелёный прогон `pytest`.

## 0. Идея одним абзацем

Каждую неделю каждый зарегистрированный пользователь бесплатно получает `WEEKLY_GRANT_AMOUNT` (по умолчанию 10 000) виртуальных долларов. В течение недели он покупает/продаёт криптоактивы по реальным ценам (публичный price-feed биржи BingX) — только спот, лонг, без плеча и без шортов. В конце недели для каждого пользователя фиксируется итоговый equity (наличные + стоимость открытых позиций по цене закрытия), строится рейтинг, топ `PRIZE_TOP_N` (по умолчанию 10) получают призы. Все открытые позиции принудительно закрываются на границе недели, новая неделя стартует с чистого баланса — история и рейтинг сохраняются, позиции не переносятся.

Это финансовая по сути система (даже если "деньги" виртуальные, а на кону реальные призы) — требования к ней как к финтех-продукту: атомарность операций, полный аудит, физическая невозможность создать баланс из ничего.

## 1. Цели и явные не-цели

**Делаем в этой итерации:**
- Полностью рабочий Telegram-бот (aiogram, только команды/инлайн-кнопки, без Mini App)
- Еженедельный цикл: начисление → торговля → закрытие → рейтинг → новый цикл
- Спот-трейдинг по всем парам BingX, лонг-онли, без плеча
- Защиту денежной логики от race condition, дублирования операций, читинга рейтинга
- Полное тестовое покрытие денежной логики

**Явно не делаем сейчас (фаза 2+):**
- Mini App / веб-интерфейс — только текстовые команды и inline-кнопки
- Плечо, шорты, лимитные/стоп-ордера — только market-ордер по текущей цене
- Переводы виртубаксов между пользователями (P2P)
- Автоматическую выплату призов — бот только фиксирует победителей и их контакты, сама выдача приза (реальные деньги/товар) — ручной процесс вне бота
- Продвинутый антифрод (device fingerprinting, ML-детекция сговора) — на MVP хватает связки "телефон + ручная проверка топа"

## 2. Стек

- Python 3.11+
- aiogram 3.x
- PostgreSQL + SQLAlchemy 2.x (async) — принципиально не SQLite: нужны `SELECT ... FOR UPDATE` под конкурентные ордера
- Alembic — миграции
- `ccxt` (async) — доступ к публичным данным BingX без ручного написания HTTP-запросов и подписи (см. раздел 7)
- APScheduler или отдельный процесс-воркер — еженедельный цикл и поллинг цен
- pytest + pytest-asyncio + реальная тестовая Postgres (testcontainers или pytest-postgresql) — денежная логика не тестируется на суррогате БД

## 3. Архитектура

```
bot/              — aiogram-хендлеры. ТОЛЬКО UI: разбор команд, форматирование ответов.
                    Никакой денежной логики напрямую — всё через services/.
services/
  trading.py      — покупка/продажа, расчёт P&L, работа с ledger
  pricing.py      — доступ к актуальным ценам (кэш + БД)
  weekly_cycle.py — еженедельный сброс, снапшоты, начисления
  accounts.py     — регистрация, верификация телефона, бан
workers/
  price_poller.py     — отдельный процесс: тянет цены с BingX, не блокирует бота
  weekly_scheduler.py — крон-джоба еженедельного цикла
db/
  models.py       — SQLAlchemy-модели
  repo.py         — репозитории с явными блокировками строк
tests/
```

Жёсткое правило: `bot/`-хендлеры не содержат SQL и не работают с деньгами напрямую — вся денежная логика тестируется без поднятия aiogram-диспетчера.

## 4. Модель данных

Типы: деньги (virtual bucks) — `NUMERIC(18,2)`. Количество актива (qty) — `NUMERIC(30,10)` (нужен запас — у дешёвых монет объём в штуках может быть очень большим). Цена актива — `NUMERIC(20,10)` (от BTC за десятки тысяч до шиткоинов по 0.0000001). Float — нигде в денежной логике.

```
users
  id                PK
  telegram_id       BIGINT UNIQUE NOT NULL
  username          TEXT
  phone_number      TEXT UNIQUE NULL          -- заполняется после верификации
  phone_verified_at TIMESTAMPTZ NULL
  rules_accepted_at TIMESTAMPTZ NULL
  is_banned         BOOLEAN DEFAULT FALSE
  ban_reason        TEXT NULL
  created_at        TIMESTAMPTZ

weeks
  id            PK
  week_number   INT
  starts_at     TIMESTAMPTZ
  ends_at       TIMESTAMPTZ
  status        ENUM('active','closing','closed')
  closed_at     TIMESTAMPTZ NULL

assets
  symbol                  PK   (напр. BTC-USDT)
  base_asset, quote_asset TEXT
  status                  ENUM('active','delisted')
  is_quote_eligible       BOOLEAN             -- участвует в призовом рейтинге
  last_24h_quote_volume   NUMERIC
  updated_at              TIMESTAMPTZ

transactions                                   -- ЕДИНСТВЕННЫЙ источник истины по деньгам
  id               PK
  user_id          FK -> users
  week_id          FK -> weeks
  type             ENUM('WEEKLY_GRANT','TRADE_BUY','TRADE_SELL','FORCED_CLOSE','ADJUSTMENT')
  amount           NUMERIC(18,2)              -- знак: + начисление / - списание
  balance_after    NUMERIC(18,2)
  ref_order_id     FK -> orders NULL
  idempotency_key  TEXT UNIQUE NOT NULL
  created_at       TIMESTAMPTZ
  CHECK (balance_after >= 0)
  UNIQUE (user_id, week_id) WHERE type = 'WEEKLY_GRANT'   -- одно начисление в неделю, без исключений

orders
  id                     PK
  user_id, week_id       FK
  asset_symbol           FK -> assets
  side                   ENUM('buy','sell')
  notional_usd           NUMERIC NULL          -- для buy: сколько виртубаксов тратим
  qty                    NUMERIC NULL          -- для sell: сколько актива продаём
  status                 ENUM('pending','filled','rejected')
  requested_at           TIMESTAMPTZ
  executed_price         NUMERIC NULL
  executed_at            TIMESTAMPTZ NULL
  price_source_timestamp TIMESTAMPTZ NULL      -- когда именно эта цена была получена от BingX
  idempotency_key        TEXT UNIQUE NOT NULL
  rejection_reason       TEXT NULL

positions
  user_id, week_id, asset_symbol   PK (composite)
  qty                              NUMERIC CHECK (qty >= 0)
  avg_entry_price                  NUMERIC
  updated_at                       TIMESTAMPTZ

leaderboard_snapshots
  week_id, user_id     PK (composite)
  rank                 INT
  cash_balance         NUMERIC
  positions_value      NUMERIC
  total_equity         NUMERIC
  created_at            TIMESTAMPTZ

prizes
  week_id, rank         PK (composite)
  user_id               FK
  description            TEXT
  payout_status          ENUM('pending','verified','paid','rejected')
  verified_by_admin_id   BIGINT NULL
  verified_at             TIMESTAMPTZ NULL
```

Для `buy`: после исполнения `qty` в `positions` увеличивается на `notional_usd / executed_price`. Для `sell`: после исполнения на баланс зачисляется `qty × executed_price`, позиция уменьшается на `qty`.

## 5. Денежные инварианты — обязательны, не опциональны

1. Баланс пользователя нигде не хранится отдельным изменяемым полем. Он всегда либо `SUM(transactions.amount) WHERE user_id=... AND week_id=...`, либо материализованный кэш, регулярно сверяемый с этой суммой (см. п. 7 ниже).
2. Любая операция, меняющая баланс или позицию, выполняется в одной DB-транзакции с `SELECT ... FOR UPDATE` на строку пользователя в текущей неделе — исключает race condition при параллельных запросах.
3. Каждая мутирующая операция несёт `idempotency_key`. Рекомендация: для действий по нажатию inline-кнопки использовать `callback_query.id` (Telegram сам гарантирует его уникальность на каждое нажатие); для команд, введённых текстом — `update_id` (тоже уникален и монотонен на уровне бота). Не изобретать свою хэш-схему без необходимости. Повторный вызов с уже виденным ключом — no-op, возвращает результат первого выполнения.
4. Buy/sell проходит проверку достаточности баланса/позиции **внутри** заблокированной транзакции, не отдельным запросом до неё — иначе между проверкой и списанием пролезет гонка.
5. Ордер исполняется по цене, полученной сервером **в момент обработки**, не по цене, которую видел клиент в интерфейсе при нажатии кнопки. Если цена в кэше старше `MAX_PRICE_STALENESS_SECONDS` — ордер не исполняется по устаревшей цене (короткое ожидание свежей котировки либо отказ с понятной причиной).
6. Еженедельный цикл — идемпотентная многошаговая операция с сохранением прогресса в `weeks.status`:
   - a) `status = 'closing'`, фиксируется единый closing-timestamp цен для всех активов
   - b) для каждого пользователя считается equity (cash + Σ qty×closing_price) → пишется в `leaderboard_snapshots`
   - c) только после успешной записи всех снапшотов — принудительно закрываются позиции (`FORCED_CLOSE`-транзакции по closing-цене)
   - d) создаётся новая неделя
   - e) только после создания новой недели — начисляется `WEEKLY_GRANT` каждому активному (не забаненному) пользователю
   - f) `status = 'closed'` на старой неделе

   Если джоба падает на любом шаге — при рестарте она проверяет текущий `status` и наличие соответствующих записей, продолжая с прерванного шага, а не начиная заново.
7. Фоновая сверка раз в час: для каждого активного пользователя `SUM(transactions.amount)` сверяется с тем, что видит бот в UI. Расхождение — критичный алерт админу, не показывается пользователю как обычная ошибка.

## 6. Анти-чит по векторам

| Вектор | Защита |
|---|---|
| Race condition на параллельных ордерах | `SELECT FOR UPDATE` + проверка баланса внутри той же транзакции (п. 5.2, 5.4) |
| Двойной тап кнопки / повторная отправка команды | `idempotency_key` на каждой мутации (п. 5.3) |
| Устаревшая цена / игра на известном движении | Исполнение только по серверной цене на момент обработки, отказ при превышении `MAX_PRICE_STALENESS_SECONDS` (п. 5.5) |
| Мультиаккаунтинг ради нескольких призов | Обязательная верификация номера через Telegram `request_contact` до первой сделки; один приз на номер телефона; ручная проверка топ-`PRIZE_TOP_N` перед выплатой |
| Сговор между аккаунтами (перекидывание баланса) | P2P-переводов нет в принципе — единственный контрагент по сделке — рынок (BingX price feed), не другой юзер |
| Манипуляция низколиквидными монетами ради рейтинга | Флаг `is_quote_eligible` на `assets`, пересчитывается раз в сутки по 24h volume (порог `MIN_24H_QUOTE_VOLUME_USDT`). В `leaderboard_snapshots` и `prizes` учитываются только сделки/позиции по quote-eligible активам; остальные монеты доступны для торговли, но не дают веса в рейтинге |
| Двойное начисление за неделю / повторный запуск крона | `UNIQUE (user_id, week_id) WHERE type='WEEKLY_GRANT'` на уровне БД — вторую запись физически невозможно вставить, даже если джоба запустится дважды |
| Торговля без верификации | Проверка `phone_verified_at IS NOT NULL` — в сервисном слое перед вызовом `trading.py`, а не только подсказкой в UI |
| Забаненный пользователь продолжает торговать | Проверка `is_banned` в том же защищённом слое, что и баланс |

## 7. Ценовой фид (BingX)

- Публичные market-data эндпоинты BingX (домен `open-api.bingx.com`) ключа не требуют.
- Рекомендация: не писать HTTP-запросы к BingX вручную, а использовать `ccxt` — у неё есть поддерживаемый клиент для BingX (публичные методы: список торгуемых пар, батч-тикеры по всем парам разом). Это снимает риск того, что зашитый в код путь эндпоинта устареет или оказался неточным — `ccxt` абстрагирует конкретные URL и обновляется независимо от этого проекта. Точные текущие пути при необходимости сверяются с официальной документацией BingX (bingx-api.github.io/docs), а не берутся "как есть" из старых примеров в интернете.
- При старте сервиса и затем раз в 24 часа — полный список активных spot-пар через ccxt → синхронизация таблицы `assets`.
- Раз в `PRICE_POLL_INTERVAL_SECONDS` (по умолчанию 2 сек) — один батч-запрос всех тикеров разом (`fetch_tickers()` в терминах ccxt), не по одному на монету.
- Раз в 24 часа — пересчёт `is_quote_eligible` и `last_24h_quote_volume` по данным 24h-тикера (объём в quote-валюте, обычно USDT).
- Если BingX недоступен: ордера, требующие цену недоступного/устаревшего актива, отклоняются понятной причиной — никогда не исполняются по нулевой/null цене и не "зависают" молча. Алерт админу при недоступности фида дольше N минут.

## 8. Команды бота

**Пользовательские:**
- `/start` — регистрация, показ правил, кнопка "Поделиться номером" (`request_contact`), явное согласие с правилами перед первой сделкой
- `/rules` — правила: лонг-онли без плеча, quote-eligible для приза, номер телефона обязателен, топ-10 проверяется вручную перед выплатой
- `/balance` — текущий кэш-баланс + время до конца недели
- `/price <symbol>` — текущая цена
- `/buy <symbol> <usd>` — рыночная покупка на сумму
- `/sell <symbol> <qty|all>` — рыночная продажа
- `/portfolio` — открытые позиции + текущий unrealized P&L
- `/history` — последние транзакции
- `/leaderboard` — live-рейтинг текущей недели (по equity)

**Админские** (проверка `telegram_id IN ADMIN_TELEGRAM_IDS`):
- `/admin_stats`
- `/admin_review_top` — список топ-`PRIZE_TOP_N` для ручной проверки перед выплатой
- `/admin_force_close_week` — ручной фолбэк на случай сбоя крона, с двухшаговым подтверждением (команда → инлайн-кнопка "Да, точно закрыть")
- `/admin_ban <telegram_id> <причина>`

## 9. Обязательные тест-кейсы

- Два параллельных `buy` на весь баланс от одного юзера — ровно один проходит, второй отклоняется по недостатку средств (тест на реальную гонку, не мок)
- Повторный вызов с тем же `idempotency_key` не создаёт вторую транзакцию/ордер
- Двойной запуск еженедельной джобы — `WEEKLY_GRANT` начисляется ровно один раз
- Падение джобы между шагами (a)–(f) из п. 5.6 — рестарт продолжает с прерванного шага, ничего не задваивается и не теряется
- Ордер отклоняется, если цена в кэше старше `MAX_PRICE_STALENESS_SECONDS`
- `sell` больше, чем есть в позиции — отклоняется
- `buy` на сумму больше баланса — отклоняется
- Снапшот рейтинга считается по единому closing-timestamp для всех пользователей
- Фоновая сверка находит намеренно внесённое расхождение (юнит-тест на саму функцию сверки)
- Торговля без `phone_verified_at` отклоняется на уровне сервиса, а не только UI
- Забаненный пользователь отклоняется на уровне сервиса
- Монета с `is_quote_eligible=False` торгуется, но не попадает в `leaderboard_snapshots`

## 10. Требования к процессу разработки

- Код — только в файлах, не в чат; финальная поставка — единый архив
- Прогон `pytest` перед сдачей обязателен, весь вывод зелёный; ослаблять или удалять assert'ы ради прохождения теста нельзя
- Денежная логика (`services/trading.py`, `services/weekly_cycle.py`, `db/repo.py`) — приоритет №1 по глубине тестового покрытия, выше чем формулировки текстов бота
- Секреты (`BOT_TOKEN`, `DATABASE_URL`, любые API-ключи) — только через переменные окружения; `.env` — в `.gitignore` с первого коммита; реальный `.env`/сессионные файлы никогда не коммитятся
- Всё, что нельзя проверить автотестом (например, живой ответ BingX в проде) — отдельным файлом с описанием, как проверялось вручную

## 12. Definition of Done

- [ ] Баланс нигде не хранится отдельным полем — везде читается/сверяется через `SUM(transactions.amount)`
- [ ] Все мутирующие операции идемпотентны (unique constraint на `idempotency_key`)
- [ ] Конкурентные ордера одного юзера не могут вместе увести баланс в минус (проверено тестом с реальной параллельностью)
- [ ] Ордер никогда не исполняется по цене старше `MAX_PRICE_STALENESS_SECONDS`
- [ ] Еженедельный цикл идемпотентен, resumable, покрыт тестом на падение между шагами
- [ ] `WEEKLY_GRANT` физически не может начислиться дважды за неделю (constraint на уровне БД)
- [ ] Рейтинг и призы считаются только по `is_quote_eligible` активам
- [ ] Верификация телефона и бан проверяются на уровне сервиса, а не только UI
- [ ] Все денежные/количественные поля — `NUMERIC`, ни одного `float` в денежной логике
- [ ] `.env` в `.gitignore`, ни один секрет не закоммичен
- [ ] Все тест-кейсы из раздела 9 зелёные, подтверждено выводом `pytest`
